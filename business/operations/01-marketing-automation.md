## 01 この設計で作る仕組み

「見込み客が調べる課題」を記事にし、SNSへ展開し、制作体験・メール・LINE相談へ案内する。公開後の数値から次の記事を選ぶところまでを一つの流れにする。

通常の記事と投稿は、最初に決めたブランド・事実・品質・費用のルールに沿って予約公開する。料金変更、顧客実績、契約条件、広告予算の変更は担当者が判断する。承認待ちと通常の自動処理を別の状態にして、担当者の不在で全処理が止まらない構成にする。

本書の「自動」は導入後の動作を指す。現在は、静的サイト・問い合わせフォーム・制作体験・料金・契約ひな形・LINEへのリンクが用意されている。CMS、アクセス解析、記事生成、予約投稿、CRM連携、広告配信は未導入。

### 最初の対象と提案

初期対象の仮案は「小規模な不動産会社」。会社紹介、売却相談、賃貸相談、管理相談など、事業用の静的サイトと問い合わせ導線を提供する。対象業種は所有者が後で変更できる設定値とする。

GARAGE HOUSE NAVIを自主制作・自社運営の制作例として紹介できるため、不動産の顧客が何を知りたいかを説明しやすい。物件データベース、検索システム、会員、独自予約、CMSは基本料金に含めない。自主制作の事例を受託実績として扱わない。

最初は日本語・国内の事業者向けとし、全国対応の内容を作る。実際に地域の知見や事例がない段階で、市区町村名だけを差し替えたページを量産しない。

## 03 記事・ページの設計

最初に業種別の案内ページを1つ作り、そのページへ関連記事をつなぐ。広告やSNSのリンク先が記事だけで終わらないよう、制作体験、料金、制作例、相談への道筋を置く。

仮のパスは `/industries/realestate/` と `/journal/記事のslug/`。これらは提案であり、現在の公開サイトにはまだ存在しない。実装時は各ディレクトリの `index.html` と、canonical・サイトマップ・内部リンクを合わせる。既存のHero・Builder・フォームは維持する。

### 業種ページに必要な情報

・誰のどの課題を解決するか。会社紹介、売却相談など静的サイトの範囲を明記。
・会社概要、対応エリア、事業内容、相談の流れ、よくある質問など、顧客が判断する情報。
・55,000円／110,000円の範囲と追加見積り。物件検索などの別対応を見分けられる説明。
・自主制作と受託実績を区分した制作例。架空の相談数・順位・顧客の声は掲載しない。
・制作体験、料金、メールまたはLINE相談の入口。

## 04 台帳と状態管理

Google Sheetsには記事台帳と配信台帳を分けて作る。本文を全セルへ詰めず、長い下書きは非公開ドキュメント等に保存し、参照先と版を管理する。下記の項目はスキーマ案であり、現在のサイトへ実装済みではない。

| 記事台帳の項目 | 役割 |
| --- | --- |
| content_id | 一意のID。例 PA-CONTENT-0001 |
| industry / intent | 対象業種・読者が解決したい疑問 |
| title / slug / canonical | 見出し・公開パス・正規URL |
| source_urls / checked_at | 根拠URL・確認日。自社の料金は確定情報から取得 |
| draft_ref / version / hash | 下書きの参照先・版・重複判定 |
| status / check_report | 状態・検査結果・停止理由 |
| scheduled_at / timezone | 公開予定、Asia/Tokyo |
| published_url / commit_sha | 実際の公開先・GitHub保存版 |
| published_at / verified_at | 公開日時と公開確認日時を分離 |

記事の状態は IDEA → RESEARCHED → DRAFT → CHECKED → SCHEDULED → PUBLISHED → VERIFIED。要確認は REVIEW_REQUIRED、失敗は ERROR、削除等は ARCHIVED。PUBLISHEDのまま検証に失敗したものを成功扱いしない。

配信台帳には `content_id`、媒体、投稿版、公開予定、実際の投稿ID、公開URL、試行回数、状態を持つ。同じ記事でも媒体ごとに状態を管理する。

重複防止キーは `content_id＋媒体＋投稿版`。実行前に台帳と実際の公開先を照合し、既に存在する投稿を作り直さない。APIが応答しなかった場合は、送信成功の可能性を調べてから再試行する。

## 05 n8nのワークフローを組む手順

### Workflow A：題材から下書き

Schedule Trigger（週1回）→ 設定・台帳の取得 → 対象業種と既存記事の照合 → 1題選定 → 公式資料・自社確定情報の確認 → AIで構成と本文生成 → 検査 → 台帳保存。

手順1：所有者のアカウントを接続する。認証情報はn8nのCredentialsへ保存し、台帳・GitHub・プロンプトに入れない。
手順2：対象業種、サイトURL、事実マスター、1週間の公開上限、予算上限、停止フラグを設定する。
手順3：記事台帳に12題を登録する。競合の文章を取得して書き換える方式にはしない。
手順4：AIは構成、記事本文、見出し、説明文、CTA案、参照した資料と未確認事項を返す。事実の確認は生成本文とは独立して実行する。
手順5：禁止表現・料金・制作期間・リンク・類似記事を機械検査し、条件によりCHECKEDまたはREVIEW_REQUIREDへ振り分ける。

### Workflow B：記事の予約公開

Schedule Trigger（毎日）→ 公開時刻と停止フラグ → CHECKEDの記事選定 → 固定テンプレートへ安全に流し込み → 専用ブランチへコミット → 検証 → 許可済み条件で反映 → 配信結果確認 → VERIFIED記録。

静的ページの本文は、安全なMarkdown/JSONを固定レンダラーでHTML化する。AIの出力を任意のJavaScript、HTML、ワークフローとして実行しない。新規記事だけの変更を許可し、`index.html`、`commerce.html`、フォーム、料金、`.github/workflows/`等の変更は拒否する。

自動公開は、最初に所有者が承認した対象パス・内容区分・検査条件に限定する。公開ブランチには必要な公開ファイルだけを反映する。現在は編集用mainと公開用gh-pagesが分かれているため、mainへのコミット成功だけを公開成功にしない。GitHub Pagesの対象コミットがbuiltになり、URLが200で、意図した本文が配信されていることを確認する。

GitHubの認証は対象リポジトリに必要な最小権限とする。自動化に管理者権限や全リポジトリ権限を渡さない。認証、保護ブランチ、GitHub ActionsからのPRや反映可否は、導入時の設定で確認する。

### Workflow C：SNS配信

VERIFIED記事 → 媒体別に短文2案生成 → 文字数・根拠・リンク検査 → UTM付与 → 予約 → 公式API等で公開 → 投稿ID・URLを保存 → 台帳更新。

投稿本文には、読者の疑問と記事で分かることを1つずつ入れる。同じ投稿を連続で大量配信しない。生成画像を実案件の写真や実績として扱わない。画像が必要なら、利用許可のある画像・自主制作の実画面・説明図から選ぶ。

### Workflow D：集計と次の題材

週1回 → Search Console・導入済みのアクセス解析・投稿サービスから数値取得 → 期間と母数を揃えて集計 → 記事・CTA改善案 → 台帳へ次の題材を登録。

「表示回数が少ない」「訪問はあるが相談に進まない」「LINEクリックはあるが相談がない」を分ける。記事の言い換えだけでなく、対象読者・提案・ページの入力負担を検討する。少数の数字で勝ち負けを断定しない。

## 06 自動公開の検査ゲート

| 検査 | 通過条件 | 不合格時 |
| --- | --- | --- |
| 情報の正確性 | 料金・納期・範囲が事実マスターと一致 | 修正後に再検査 |
| 実績・数字 | 許可済みの区分と実測値のみ | REVIEW_REQUIRED |
| 参照資料 | 主張と根拠が対応し、引用量・利用条件に問題がない | 資料を追加するまで停止 |
| 独自性 | 実務のチェックリストや判断材料があり、既存記事の重複ではない | 題材を統合・再構成 |
| 読みやすさ | 読者の疑問に答え、過剰な煽り・無意味な長文化がない | 再編集 |
| 技術 | 未エスケープHTML・実行コードなし、リンク正常、canonical適切 | 公開不可 |
| 相談導線 | 記事から業種ページ・制作体験・相談へ進める | CTAを修正 |
| 個人情報 | 顧客の情報、問い合わせ内容、認証情報が含まれない | 隔離して通知 |
| 公開状態 | 許可パスだけの変更、対象ビルドとURLを確認 | ERROR・通知 |

AIの「問題なし」という自己評価だけで通過させない。価格などは固定値照合、参照は根拠確認、技術は実際のファイル・ブラウザ・HTTPで検査する。

法律・税務・不動産取引上の具体的な助言、顧客名入りの事例、新料金、値引き、制作保証などは通常記事の自動公開対象から外し、確認キューに送る。正常な一般記事は予約公開できる設計とする。

## 07 問い合わせと制作の自動化

問い合わせ内容は記事台帳と分離する。現行フォームはFormSubmitからGmailへ、LINEは公式アカウント内で受信する。LINEのリンクを置いただけでは、その相談がGmailやCRMへ自動で入るわけではない。

Gmailのラベル等で一次分類する案は、所有者の非公開アカウントに設定する。LINE Messaging API連携は別の設定が必要。Webhook署名を検証し、イベントIDを重複処理しない。チャンネルの費用・配信枠・権限・連絡先の扱いを確認してから導入する。

自動処理の対象は「受付記録、受信案内、要約の下書き、ヒアリング項目、見積り下書き、確認期限の通知」。個別の価格確定、契約成立、請求、入金確認、公開承認は案件の記録と担当者の判断に基づく。AIに銀行入金を推定させない。

顧客の相談内容を別のAI・CRM・自動化サービスへ送る前に、利用目的、委託・外部サービスの扱い、アクセス範囲、保存期間を決め、必要な説明・契約・プライバシー案内を揃える。現在の問い合わせ案内を変更せず、新しい送信先を追加したことにしない。プロンプトには案件IDと匿名化した内容を使う。

## 08 広告と配信費用

広告は初期設定でOFF。記事・相談ページ・実受信・計測の確認後に、所有者が予算・対象・期間・停止条件を決めて開始する。Google検索広告は「Webサイト制作を検討している事業者」の検索意図に寄せる案とし、物件探しの消費者向け検索とは分ける。

広告文生成と集計は自動化できる。広告アカウント、課金設定、入稿の審査、計測、費用は別途必要。予算の自動増額や、新しいターゲットへの自動拡大は初期案に含めない。API対応と権限は導入時に公式資料を確認する。

| 必須設定 | 初期案 |
| --- | --- |
| ads_enabled | false |
| monthly_budget_yen | 未設定。所有者が決めるまで出稿しない |
| daily_budget_yen | 媒体の配信ルールを確認し、月の許容額に合わせて設定 |
| spend_alert | 月の許容額の80％で通知する案 |
| stop_condition | 計測不良、予算超過の恐れ、誤った広告文、相談先の障害で停止 |
| approval_ref | 許可した予算・対象・期間の記録 |

媒体の日予算は「毎日その額で厳密に止まる上限」とは限らない。契約した媒体の課金・配信仕様を確認し、利用可能な支出制限・残高設定と監視を合わせる。通知だけで支出が確実に止まるとは扱わない。

## 09 効果測定と障害時の処理

UTMの例：`utm_source=linkedin&utm_medium=social&utm_campaign=realestate_guide&utm_content=article_01_a`。UTMには顧客名・メール・電話番号を含めない。URLを付けるだけでは訪問や受注が自動集計されないため、計測機能を実装・確認する。

| 数値 | 定義 |
| --- | --- |
| 検索クリック | Search Consoleの対象URL・期間のクリック |
| 記事の訪問 | 導入した解析の定義に基づくセッション等 |
| form_success | 送信サービスの成功応答。実受信とは別に管理 |
| line_click | LINEリンクのクリック。友だち追加や実相談の数と区別 |
| 有効相談 | 受信内容を確認し、対象事業と制作検討が分かった相談 |
| 成約 | 条件に合意した契約。売上・入金とは区別 |
| 入金 | 銀行等で実際に確認した入金 |

相談率＝有効相談数÷対象の訪問数、成約率＝成約数÷有効相談数、広告の相談単価＝広告費÷広告経由の有効相談数。異なる期間や媒体の数字を混ぜない。0件や少数の期間では、母数不足も併記する。

障害処理は「エラー分類→限定的な再試行→台帳へ記録→通知」。タイムアウトや一時的な5xxは上限3回・間隔を広げて再試行する案。認証エラー、利用枠超過、料金誤記、個人情報の検出は自動再投稿せず停止する。

二重公開を防ぐロック、公開済みIDの照合、日次の実行上限を設ける。実行ログには必要な状態とIDだけを残し、認証情報や相談全文を保存しない。すべてを止める `automation_enabled=false` と、記事・SNS・広告それぞれの停止フラグを用意する。

誤情報を公開した場合は投稿IDと公開版を特定し、取り下げ・訂正を行う。GitHubは直前の正常版を基準に修正コミットで戻す。強制pushや無関係な変更の上書きを復旧手段にしない。

## 10 導入の順番と受入条件

### 第1週：接続と、記事1本の通し運転

所有者が対象業種・媒体・予算・サービスを確定し、本人の非公開アカウントを用意する。初期の事実マスター、公開パス、台帳、停止フラグを設定する。記事1本を下書きから検証済み公開まで通す。最初の3記事は、所有者が内容を確認して判定ルールを調整する。

### 第2週：予約投稿と集計

SNS1媒体へ接続し、記事から2投稿を作る。タイムゾーン、予約日時、APIエラー、二重投稿、停止フラグを試す。解析を導入する場合は説明と同意の要否を確認して実装し、個人情報を送らないことを確認する。週次集計を作る。

### 第3〜4週：通常記事の自動公開

検査を通った通常記事のみ予約公開する。例外は確認キューへ送る。投稿数より、読者の疑問に答えているか・有効相談につながるかを確認する。問い合わせ受信が確認できてから広告の小規模な検証を検討する。

### 運用開始前に実施する確認

・同じワークフローを2回実行しても記事・SNSが重複しない。
・存在しない参照資料、料金違い、顧客名、禁止パス変更が検査で止まる。
・mainへ保存しただけでは公開済みにならず、対象ビルドとURL確認でVERIFIEDになる。
・スマホ390px、PC1200px・1440pxで記事・CTA・フォームが使える。
・SNS投稿に実際のURLと投稿IDが残り、元記事との対応が追える。
・API認証切れ・利用枠超過・停止フラグで追加公開が止まる。
・相談数にLINEクリックを混ぜない。個人情報が解析や記事に入らない。
・所有者が資格情報の解除、全停止、投稿の訂正、GitHubの復旧を実行できる。

### GitHub連携の実装入口

GitHub REST APIの例は、最新mainの参照取得、専用ブランチ作成、記事ファイル保存、PR作成。対象は `eyueyu0806-sys/website-studio` に限定する。導入時に認証方式と保護設定を確認する。

```text
GET /repos/{owner}/{repo}/git/ref/heads/main
POST /repos/{owner}/{repo}/git/refs
PUT /repos/{owner}/{repo}/contents/{article_path}
POST /repos/{owner}/{repo}/pulls
GET /repos/{owner}/{repo}/pages/builds/latest
```

公開ジョブは、記事パスだけの変更、リンク/ファイル検証、個人情報なし、固定サービス条件との一致を確認する。通常記事の反映を自動にする場合も、事前に許可した公開ルールの対象か判定する。個別に未承認のコード変更を自動でマージしない。

ジョブの同時実行を記事ID単位で制御する。公開前に最新gh-pagesを取得し、正常なファイルを保つ。競合した場合は最新状態へ戻って再検証し、強制pushで回避しない。公開先への書込み成功後に停止した場合は、再開時に対象コミットと記事URLを調べて二重公開を防ぐ。

### 通し運転のチェックケース

```text
ケース1：正常記事 → 保存 → 本番反映 → URL確認 → SNS予約 → 実投稿ID保存。
ケース2：同じcontent_idを再実行 → 既存版を検出し、新しい投稿を作らない。
ケース3：料金を49,800円へ改変 → 検査不合格、公開・SNSへ進まない。
ケース4：顧客名やメールを本文へ混入 → 確認キューで隔離する。
ケース5：AI APIの429/5xx → 上限内で再試行。課金と重複生成を確認する。
ケース6：GitHub保存済み、本番反映前に停止 → 状態から再開し、公開済みと誤記しない。
ケース7：本番成功、台帳更新前に停止 → 実公開版を照合し、二重反映を防ぐ。
ケース8：SNS API応答なし → 投稿の有無を調べ、未確認のまま再投稿しない。
ケース9：automation_enabled=false → 新しい公開・投稿・広告操作が止まる。
ケース10：解析未導入 → 訪問を0件と創作せず、未計測として報告する。
```

この通し運転を匿名のテスト記事とテスト設定で行い、本番の広告課金や実際の営業連絡をテストで発生させない。テスト結果、資格情報の管理者、停止操作を所有者へ渡してから運用を開始する。
