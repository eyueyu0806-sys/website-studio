# 受注から納品までの運用手順書

Page Atelier / 専門サイト工房
2026年10月7日版・個人事業で提供する事業用の静的Webサイト制作

## 01 今日から使う手順

この手順書は、無料相談を受けてから、見積り、契約、制作、修正、入金、公開、引渡しまでを運営者本人が進めるためのもの。担当者を増やす場合は顧客情報へのアクセス方針を先に変更する。

制作の目安は、仕様・必要素材・着手金が揃った開始日から2週間（14日間）。営業日14日ではない。無料相談を受けた日や、見積書を送った日から数えない。確定した公開日は案件ごとの見積書・契約書で合意する。

問い合わせは契約成立ではない。AIで作った見積り・契約・文章・コードも、確認なしで確定したものとして送付・公開しない。

### 受注に必要な5つの記録

1. 何を作るか：ページ・掲載量・機能・フォーム・公開先・対応環境。
2. いくらか：税込総額・外部費用・50％ずつの支払額と期限。
3. いつか：素材提供日・開始条件・確認日・公開日。
4. どう確定したか：同じ版の契約書・見積書・別紙への明示的な合意。
5. 何を渡すか：ソース・アカウント・ドメインの管理・更新方法・サポートの有無。

### 標準サービスの境界

| 項目 | 運用する条件 |
| --- | --- |
| 1ページ | 税込55,000円、1ページ・8セクションまで |
| 小規模サイト | 税込110,000円、トップを含む5ページまで |
| 共通範囲 | 構成・デザイン・スマホ対応・公開・検索向け基本設定・フォーム1つ・地図・外部予約/SNSリンク |
| 素材 | 原稿・写真は顧客支給が基本。AIによる編集支援は、原稿をゼロから制作する契約と区別 |
| プライバシーページ | 顧客が支給する原稿1ページを、プランのページ数の外で料金内に掲載 |
| 修正 | 軽微な修正2回。まとめた要望への対応を1回とする。制作ミス・仕様不一致は回数外 |
| 追加 | 既存デザインの追加ページ16,500円〜。3回目以降の軽微な修正5,500円〜。事前合意が必要 |
| 個別見積り | CMS・決済・会員・物件等の検索・独自予約・新規原稿作成・撮影・大幅変更 |
| 支払い | 銀行振込。着手前50％、最終確認後・公開前50％ |
| 維持費 | ドメイン・サーバー・有料サービス等は別。負担者と更新日を記録 |
| 更新サポート | 任意で月5,500円、月2回・合計60分、繰越なし。別の申込書で合意 |

制作体験が提案する機能を、標準料金ですべて実装する約束にしない。「検索」「予約」の希望は、外部サービスへのリンクなのか、独自システムなのかを確認する。

## 02 案件台帳と非公開の作業場所

案件IDの例は PA-2026-001。実際の顧客名を含めないIDにする。記入済みの契約・銀行情報・相談内容は、GitHubや公開サイトに保存しない。本人だけが管理する非公開フォルダに保存する。

### フォルダの初期構成

```text
PA-2026-001/
  01-consultation/   相談・ヒアリング・匿名化した要約
  02-agreement/      確定見積書・契約書・合意記録
  03-materials/      支給原稿・画像・素材の利用許可
  04-design/         構成案・デザイン案・確認記録
  05-review/         修正一覧・承認記録・検証報告
  06-delivery/       納品ZIP・更新手順・引渡し一覧
  07-support/        別契約のサポート記録
```

公開してよいソース・画像と、上記の顧客情報を分ける。素材に住所・氏名が含まれる場合は公開許可された会社情報か確認する。パスワードはフォルダ内の平文メモにも入れず、必要なアクセスを招待・最小権限で受ける。

| 台帳項目 | 記録すること |
| --- | --- |
| 案件ID・状態 | 現在の工程・次の操作・担当者 |
| 顧客と決裁者 | 非公開の正式情報、最終承認できる人 |
| 依頼と範囲 | 業種・目的・ページ・掲載量・機能・対象外 |
| 金額と支払い | 税込総額、外部費用、着手金・残金の請求と実入金 |
| 日付 | 素材期限、開始条件充足日、確認期限、公開予定 |
| 書類の版 | 見積番号、版、契約書名、双方の合意記録 |
| 素材・アカウント | 未着一覧、利用許可、公開先の所有者 |
| 修正 | 依頼日、対象、軽微/追加/不具合、回数、完了 |
| 承認・公開 | 顧客承認の対象版、公開コミット、URL、確認日 |
| 納品とサポート | 引渡し日、受領確認、任意サポートの別契約 |

状態は CONSULTATION → SCOPED → QUOTED → AGREED → START_READY → BUILDING → CLIENT_REVIEW → REVISED → FINAL_APPROVED → BALANCE_CONFIRMED → PUBLISHED_VERIFIED → DELIVERED。素材待ち・回答待ち・入金待ちは状態と理由を記録する。キャンセルはCANCELLEDとして精算記録を残す。

## 03 無料相談から見積りまで

### 受付当日：確認する

受信先は yue.sadamatsu@gmail.com、LINEは https://lin.ee/VZsDkE9 。メールとLINEの両方から同じ相手が来た場合は1つの案件にまとめ、重複見積りを防ぐ。受付への返信と、広告配信への同意は別に扱う。

最初に聞くのは、業種、作りたいもの・困りごと、既存サイトURL、希望時期。必要なら次に、ページ数、素材の有無、担当者と決裁者、予算、公開先を聞く。初回から身分証・自宅住所・銀行情報・パスワードを求めない。

電話や会議を行った場合も、決定事項・未決事項・次の操作をメール等へ残す。録音や別のAIへの相談全文の送信を、同意なしに前提としない。

### 適合判断

標準で対応できる静的サイトか、別見積りか、専門家・別サービスが必要かを分ける。納期や技術が不明なものを、受注したい気持ちだけで「全部できます」と約束しない。

既存サイトの改修は、所有者・コード/素材の権利・更新方法・引渡し可能範囲を確認する。他社サイトを少し変更して新規制作として納品しない。顧客が所有するコードでも第三者素材やライブラリの利用条件は確認する。

### スコープシートを作る

ページ名、各ページのセクションと掲載量、必須機能、フォーム項目と実際の受信先、地図、外部予約・SNS、ロゴ・原稿・写真、対応ブラウザ、公開先、SEO基本設定、納品物、対象外、顧客が操作する箇所を列挙する。

ログイン、データ保存、決済、予約枠の管理、メールサーバー構築等の有無は明確にする。顧客が「フォーム」と言っても、メール転送かCRM登録か業務システムかで範囲が異なる。

見積りの出力は、標準プラン＋合意した追加＋外部実費を分ける。単価が「〜」の追加は、実際に担当者が確定した額を使う。AIが最安値を自動で契約価格にしない。

### 法人の発注・経理の確認

実際に契約する法人名、担当者、決裁者、請求先、発注書の有無、社内稟議、支払締め日を確認する。相手の「月末締め翌月払い」等が標準の着手前50％・公開前50％と異なる場合は、受注前に個別条件として合意して書類を揃える。支払い条件が未決のまま先に制作を始めない。

先方の契約書や秘密保持契約がある場合は、範囲・権利・公開可否・責任・AIや外部サービスへの情報提供・支払いを自社条件と照合する。AI利用を許可していない資料を別サービスへ送らない。内容の確認が必要な条項は、署名する前に専門家等へ相談する。双方の契約書が食い違うまま二重に締結しない。

## 04 見積書・契約・開始条件

`business/estimate-template.xlsx`、`website-production-contract.docx`、必要なら`optional-update-support.docx`を、非公開の案件フォルダへコピーして記入する。ひな形の公開版へ顧客情報を書かない。

見積書には正式な運営者名・住所・連絡先・振込先、相手の正式情報、案件名、範囲、税込料金、外部費用、工程内訳、具体的な納期・確認日・支払日を入れる。適格請求書発行事業者番号は登録している場合だけ実際の番号を使う。見積書を請求書・領収書と混同しない。

契約書の当事者欄・別紙・見積書の版と金額を揃え、空欄・プレースホルダー・例文が残らないよう確認する。契約前に「納品するもの」「顧客が用意するもの」「別料金」を読める状態にする。

署名・電子署名、または同じ確定版一式を特定した明示的なメール承諾を記録する。双方の合意を残し、曖昧な「了解」だけで作業開始しない。口頭の追加依頼も文書で確認する。

### 開始チェック

・確定範囲と公開予定日への双方の合意がある。
・必要な原稿・写真・ロゴ・会社情報が揃い、利用権を確認した。
・公開先のアカウントと管理者、ドメイン、サービス費用を確認した。
・銀行等で着手金の実入金を確認した。振込予定や送金画面だけで入金済みにしない。
・フォームの受信者、外部サービス、プライバシー原稿、承認する人が分かっている。

全部揃った日を開始日として連絡し、14日間目安と個別に合意した日程を再確認する。揃っていない場合は素材待ち等のままにし、開始日を作らない。

## 05 2週間の制作計画

下記は内部の工程配分案。顧客の返答が早い場合の目安であり、契約上の確認回答期間を短縮するものではない。契約ひな形の回答期限は原則5営業日。各確認に5営業日を使う案件では、見積り時に待ち時間を含む日程へ調整する。無回答を自動承認として公開しない。

| 時期 | 作業 | 次へ進む条件 |
| --- | --- | --- |
| 開始前 | 合意・素材・着手金・アカウント | 開始チェックがすべて完了 |
| Day 1〜2 | ヒアリング整理・構成・導線・デザイン方針 | 契約範囲と構成が一致し、重要な未決事項がない |
| Day 3〜5 | 静的サイト実装・支給素材反映 | 必須ページ・フォーム・スマホ表示が用意できる |
| Day 6 | 内部確認後、初稿を提示 | 顧客が安全に見られる確認環境と、確認項目が揃う |
| Day 7〜9 | 1回目のまとめた修正 | 要望を分類し、追加範囲は別途合意 |
| Day 10〜11 | 2回目の軽微な修正・QA | 残る内容変更と不具合が分かれている |
| Day 12〜13 | 最終承認・残金請求/入金・公開準備 | 承認した版と実入金が一致 |
| Day 14目安 | 公開・実受信・引渡し | HTTPS・必須機能・納品物を実確認 |

土日祝、顧客の回答期間、銀行の営業日、DNSと証明書発行を考慮して実際の日付へ落とす。夜間に作業できることを、常時即答できる約束にしない。

日程に影響が出ると分かった時点で、理由、影響する作業、変更予定日、追加費用の有無を連絡し、合意を記録する。担当者側の遅れも同じように説明する。納期延長をAIが勝手に送信・確定しない。

## 06 AIを使う制作の順番

別冊「AIプロンプト集」の共通ルールと、案件ブリーフを毎回渡す。会話が長くなったら、確定事項・未決事項・変更履歴・次の工程を保存して、新しい会話でも再開できるようにする。

1. 相談の匿名化・整理。AIには顧客の秘密情報やログイン情報を渡さない。
2. ヒアリングとスコープを作る。未回答の重要事項を分ける。
3. 料金の範囲、見積書と契約の整合を確認する。正式書類は担当者が確定する。
4. サイトマップ・ワイヤーフレーム・文章の編集・デザイン方針を作る。
5. 合意した構成を実装する。既存のコードがある場合は確認・差分編集から始める。
6. フォーム・レスポンシブ・アクセシビリティ・SEO・素材条件を検証する。
7. 顧客のまとめた修正を分類し、合意した範囲だけを直す。
8. 公開チェック、納品説明、更新手順を作る。最終承認と入金を実記録で確認する。

AIに一度でサイト・法律文・契約・料金・公開を全部決めさせない。各工程で入力と成果物を固定し、作業が変わったら前提も更新する。

## 07 初稿と修正の運用

初稿を見せる前に、内部で誤字・未支給素材・フォーム・390px表示・リンク・JavaScript例外を確認する。仮の会社情報・電話・料金・顧客の声を、見た目を埋めるために作らない。未支給は作業中と明記し、公開前に解消する。

確認環境は、顧客情報の内容に合わせて認証や閲覧制限を使う。推測しにくいURLやnoindexだけを機密保護として扱わない。無断で顧客の非公開情報をGitHub Pagesへ仮公開しない。

顧客へ「ページURL、版、確認項目、まとめて返す方法、契約と整合する回答期限」を送る。修正依頼はスクリーンショット・ページ名・対象箇所・希望を1つの一覧にまとめてもらう。

| 分類 | 例 | 扱い |
| --- | --- | --- |
| 軽微な修正 | 支給文の差替え、画像交換、配色の小調整 | 契約範囲内の2回へ計上 |
| 制作ミス | 誤反映、壊れたリンク、合意した仕様に不足 | 回数に計上せず修正 |
| 追加作業 | 新規ページ、検索、決済、大幅な構成変更 | 費用・範囲・納期を事前合意 |
| 未決事項 | 支給文が未確定、受信先が不明 | 確定してから実装・公開 |

「2回」の残数と、今回の依頼一覧を顧客と共有する。追加費用を事後に請求しない。不具合を3回目の修正として扱わない。

## 08 技術・内容の受入チェック

### 内容と権利

会社名・住所・電話・メール・営業時間・事業内容・料金・資格・許認可番号・ロゴは、顧客の支給情報と照合する。第三者の写真・コード・フォントの利用条件を記録する。架空の実績、実在しない推薦、誇張した保証を載せない。

法務ページは顧客の原稿・確認した条件に基づく。AIだけで「法的に完全」と判断しない。料金、個人情報の扱い、外部送信先が実装と一致するかを確認する。

### 表示と操作

PC1440px・1200px、スマホ390pxを実ブラウザで確認する。必須ページ、ヘッダー、主要CTA、文章の折返し、横方向のはみ出し、フォーム、表示の重なり、画像の欠落、エラーを確認する。必要な主要ブラウザは見積りで合意し、少なくとも手元の実スマホでも確認する。

キーボードでリンク・ボタン・フォームを操作でき、フォーカスが見えること、見出しの順序、入力ラベル、意味のある画像の代替文、読みやすいコントラスト、動きを減らす設定に配慮する。確認した範囲を記録し、検証していない規格適合を保証しない。

### フォーム

入力チェック、同意、実際の受信先、返信先、本文、必要な添付、二重送信防止、成功と失敗の案内、失敗時の入力保持を確認する。通常の自動検証では送信サービスの応答を差し替える。

本番の実送信は顧客と時刻・内容を合意し、顧客の受信者がメール到着を確認する。FormSubmit等で初回承認が必要なら承認後に再送し、本文・返信先・構成等を確認する。APIの200応答だけで受信完了としない。個人情報を含まないテスト名・本文を使う。

### 公開と検索向け基本設定

HTTPS、ドメイン、HTTP/HTTPSとwwwの転送、canonical、title・description、OG、robots、サイトマップ、実在するページの内部リンク、404、画像・フォント、コンソールとネットワークエラーを確認する。noindex・仮URL・確認用情報が本番に残っていないか確認する。

構造化データは実際の事業・ページと一致するものだけ使う。偽の評価やレビューを作らない。Googleの所有権確認とインデックス要求は顧客のアカウントで行い、実際の掲載状態と区別する。検索順位を納品の保証条件にしない。

## 09 最終承認・公開・納品

最終承認には、対象URL/ファイル、版、修正完了、公開内容、承認者、日時を記録する。メールやLINEの内容を案件に紐づけ、別の版の承認を流用しない。

承認後に残金を請求し、実入金を確認する。未入金や重要な不具合、未確定の会社情報・フォーム受信先がある場合は公開待ちとする。公開予定に影響がある場合は連絡して合意する。

### GitHub等で公開する場合

作業前に現在のブランチ・差分・指示を確認し、未保存の変更を保護する。既存リポジトリを一から作り直さない。レビュー済みの変更を保存し、公開先の最新状態を取得して意図したファイルだけ反映する。main等への保存と、本番への反映は別の操作として記録する。

本番の対象コミット・ビルド成功・HTTPS応答・配信内容を確認する。秘密情報・契約・請求書・確認画像・開示用情報を公開ファイルへ含めない。障害時は正常版と原因を確認し、修正コミット等で復旧する。強制pushで他人の変更を消さない。

### 引渡し一式

・公開URL、納品日、確定版、検証した環境と結果。
・ソースコード一式と編集場所、公開方法、変更履歴。
・ドメイン・ホスティング・フォーム・外部予約・解析の管理者と費用・更新日。
・原稿/写真の差替え手順、フォーム受信確認、公開後の復旧方法。
・素材・フォント・ライブラリの利用条件。
・対応する初期不具合の窓口、任意サポートの有無と別契約。

顧客のアカウントを基本にし、必要な所有者・権限の引渡しを確認する。パスワードを納品ZIPや公開GitHubに入れない。実際に顧客が編集場所へアクセスでき、問い合わせを受信できることを確認する。

初期の不具合確認期間はひな形で30日を案としているが、法令上の権利が30日で消えるものではない。範囲外の追加・更新は見積りか別サポートで合意する。

## 10 例外・キャンセル・事故

素材・返信・入金が遅れている場合は、未完了項目と影響を文書で連絡する。契約上の回答期限内の対応を、一方的に遅延と扱わない。開始前の必要条件が揃わない間は制作開始を記録しない。

追加依頼は、変更内容、追加料金、納期、既存作業への影響を先に確認する。AIが作成した変更提案は下書きで、相手との合意後に台帳・仕様・工程を更新する。

キャンセル時は契約の条件に従い、工程金額、実施割合、作業記録、承諾済み実費を根拠に精算する。未実施分や未合意の費用を請求せず、余剰金の返金期日を記録する。契約ひな形の初期案は精算合意後10営業日以内。制作側の不履行は顧客都合と区別する。

漏えい・誤送信・不正アクセス・公開事故があれば、対象と影響を特定してアクセスを止め、記録を保全する。顧客への連絡、認証情報の失効・再発行、必要な報告を判断する。修正前に「問題なし」と連絡しない。

運営者本人が不在のときは、受付案内と処理停止の範囲を決める。無人で契約を確定、請求額を変更、本番を公開する仕組みにはしない。繁忙時は新規開始日の調整や受付制限を行う。初期は同時進行1案件を目安に、実作業時間を記録して増やす。

## 12 案件終了後の改善

予定と実際の作業時間、修正回数、詰まった工程、外部費用、問い合わせから契約までの経路を記録する。工数が膨らんだ理由を分類し、次の見積りや開始条件に反映する。

制作例として掲載したい場合は、URL・名称・画面・説明文・担当範囲・数字を提示して許可を取得する。許可前に公開しない。初期の契約ひな形は掲載を許可しない設定としている。

同意があれば顧客の感想を原文と許可内容に沿って掲載する。感想や成果数値をAIに作らせない。紹介を依頼する場合も、顧客との関係と許可された連絡に合わせて個別に行う。

## 13 運用開始前の準備

正式な運営者情報・振込先を非公開の書類コピーへ記入する。初回の請求書・領収書の形式と税務上の扱いを確定する。受信通知、返答できる時間、素材共有、確認環境、アカウント招待、バックアップ、納品フォルダを一度自分で通して確認する。

本書・プロンプト集は初期の運用案。顧客に送る確定条件は、記入済みの見積書・契約書・別紙と双方の合意を基準にする。書類の改定で既存契約を自動変更しない。
